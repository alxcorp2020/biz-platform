- **로그인/가입 화면 깜빡임(FOUC) 제거 + 카드 중앙정렬 수정**: 직전 라우트 접근제어 작업에서 나온 UI 버그 2건. (1) 페이지 로드/이동마다 사이드바 있는 레이아웃이 잠깐 보였다 사라지는 현상 — 원인 두 가지를 각각 수정. 정적 `<body>`에 처음부터 `app-booting` 클래스를 박아 앱 셸(사이드바/헤더/탭바/전역배너)을 `visibility:hidden`으로 가리고 그 위에 로딩 스피너 오버레이만 보이게 했다가, `await loadMe(); route();`가 완전히 끝난 뒤에야 같은 동기 틱에서 클래스를 제거(초기 로드 FOUC). `route()`가 `#/` 경로일 때 `renderHome`의 비동기 대시보드 API 응답(401 감지)을 기다리지 않고, 이미 확정된 `currentUser` 값으로 `is-landing` 여부를 그 자리에서 동기적으로 결정하도록 변경(네비게이션 시 깜빡임). (2) 로그인/가입 카드가 화면 오른쪽으로 치우쳐 보이던 버그 — `body.is-auth main#app`이 `display:flex`인데 `flex-direction`을 지정 안 해 기본값 `row`로 동작, 형제 요소였던 로고(`<a class="auth-page-logo">`)와 카드(`.auth-card`)가 나란히 배치되면서 전체 그룹이 중앙에 있어도 로고가 왼쪽·카드가 오른쪽으로 나뉘어 보였던 것. 로고를 카드 형제가 아니라 카드 안쪽 최상단으로 옮기고, `main#app`에 `flex-direction: column` 추가, `.auth-card`의 `border-radius`를 하드코딩 값(14px)에서 공용 토큰 `--radius-card`(20px)로, padding을 2rem→2.5rem로 확대, 배경을 `--bg`→`--bg`에서 `--bg-soft`로 내려가는 은은한 그라데이션으로 변경. 로컬 검증: 네트워크를 인위적으로 늦춘(`Network.emulateNetworkConditions`) 상태에서 로딩 중간 시점을 캡처해 셸이 전혀 안 보이고 스피너만 뜨는 것을 로그인 상태/비로그인 상태(랜딩) 양쪽 다 스크린샷으로 확인, 로그인/가입 카드가 화면 정중앙(수직+수평)에 로고-제목-폼 순서로 표시되는 것 확인.
- **라우트 접근제어 정리**: 비로그인 상태에서 `#/notices`(공고검색) 등 내부 화면이 그대로 노출되던 문제 수정. 조사 결과 `#/notices`는 서버(`handleListNotices`)가 원래 비로그인도 200을 주는 옵셔널 인증 설계인 데다, 프론트가 상태코드를 보존 안 하는 `fetchJSON`을 써서 401 감지 자체가 불가능한 구조라 실제로 데이터가 새고 있었음(`#/pipeline`/`#/calendar`/`#/growth` 등 나머지는 서버가 401을 강제하고 프론트도 리다이렉트 코드가 있어 결과적으로는 안전했으나, 각 render 함수가 API 응답을 받은 뒤에야 뒤늦게 리다이렉트하는 분산된 방식이었음). `route()` 함수 진입 시점에 화이트리스트(`PUBLIC_ROUTES`) 기반 가드를 추가해 렌더 시작 전에 즉시 차단하는 방식으로 통일 — 공개: `/`, `#/announcements`(+상세), `#/terms`, `#/privacy`, `#/auth/login`, `#/auth/signup`, `#/invite`, `#/billing/plans`(요금비교는 가입 전에도 봐야 함), `#/billing/fail`. 나머지 전부(`#/notices`, `#/pipeline`, `#/calendar`, `#/notifications`, `#/me/*`, `#/growth`, `#/admin/*` 등)는 비로그인 시 `#/auth/login`으로 즉시 리다이렉트. **선행 버그 수정**: `loadMe()`(비동기)가 `await` 없이 호출되고 바로 `route()`가 실행되던 부팅 순서 때문에, 가드를 그대로 추가하면 실제 로그인 사용자도 새로고침마다 한 박자 로그인화면으로 잘못 튕기는 레이스컨디션이 있어 `await loadMe(); route();` 순서로 고침.

- **AI 분석 한도 차감 정책 전면 변경(폐기 후 교체)**: "실패해도 API를 호출만 했으면 한도가 차감된다"던 기존 정책(2026-07-31 확정, 8-02 재확인)을 사용자가 명시적으로 폐기하고 "실패는 어떤 이유든 절대 한도를 차감하지 않는다"로 교체. `countAIAnalysisThisMonth`(billing.go)가 이제 `extraction_status='success'`인 행만 세도록 조건 추가 — `checkAIAnalysisQuota`/`#/ai-usage`의 `usedCount`(이전엔 `len(items)`로 실패까지 세던 버그성 로직이었음, 이번에 바로잡음)/대시보드 요약 카드 전부 이 함수 하나를 공유하므로 한 번에 일관되게 바뀜. 실패 이력 자체(items 목록, 배지, 실패사유)는 그대로 다 보여준다 — 안 세는 건 오직 "이번달 사용량" 숫자뿐. **비용 남용 방지**: 한도가 더 이상 방어막이 안 되므로(실패는 무한정 시도해도 공짜), 같은 조직·같은 파일 해시로 최근 1시간 안에 3회 이상 실패하면 그 파일에 한해 신규 업로드든 재시도든 차단(`checkFileRetryRateLimit`, 429 `file_retry_blocked`) — 배치/타이머 없이 "최근 1시간 안의 실패 횟수"를 조회 시점마다 다시 세는 방식이라 오래된 실패가 자연히 창(window) 밖으로 밀려나면 저절로 재시도가 풀린다. 문구도 전부 갱신: "이번 시도는 AI 분석 한도에서 차감되었습니다" 표현을 전부 제거하고 실패 메시지를 "분석에 실패했습니다. 직접 입력해주세요. (한도가 차감되지 않았습니다)"로 통일. 로컬 검증: 같은 파일로 3회 연속 실패시켜 한도(`usedCount`)가 0에서 전혀 안 움직이는 것 확인, 4번째 시도는 429로 차단되는 것 확인, 다른 파일(다른 해시)은 차단 안 되는 것 확인, DB에서 한 건을 success로 표시해 그 건만 정확히 usedCount에 반영되는 것(1건, items는 계속 4건 전부 표시) 확인
- 관리자 회원관리 기능 확장 4종. - AI 분석(증빙서류 업로드) 성공/실패 이력을 DB에 남기고 사용내역 화면에서 확인 가능하게 개선 — 이전엔 실패해도 한도가 차감된다는 사실은 업로드 시점 에러 메시지에만 잠깐 보이고 DB엔 아무 기록이 안 남아, 사후에 어떤 시도가 실패했는지 확인할 방법이 없었음(재확인 조사에서 발견). `company_documents`에 `extraction_status`('success'/'failed', NULL='처리중')·`failure_reason`(사용자 친화적 문구, API 원본 에러 텍스트는 절대 노출 안 함 — `classifyExtractionFailureReason`이 "claude api error"/네트워크 에러류는 "일시적 오류", "parse tool input"/"no tool_use block"류는 "문서 인식 실패"로 매핑) 컬럼 추가. 6개 업로드 카테고리(면허·인증/재무제표/실적증명/인력/지식재산권/4대보험) 전부 Claude 호출 직후 이 컬럼을 갱신(`markDocumentExtractionResult`). `#/ai-usage` 화면: 항목마다 성공/실패/처리중 배지 + 실패 시 failure_reason 표시 + 실패 항목에 "재시도" 버튼 추가. 재시도는 디스크에 이미 저장된 원본 파일을 재사용해 새 멀티파트 업로드 없이 바로 재분석하되, 새로운 시도이므로 `company_documents`에 새 행을 만들어 한도도 새로 차감(원래 실패 행은 이력으로 그대로 남김) — 재시도 성공 시 그 자리에서 바로 해당 카테고리의 확인/저장 폼(기존 업로드 플로우와 동일한 컴포넌트 재사용)을 띄워 한 번 더 업로드하지 않고도 저장까지 이어짐. 로컬 검증: `ANTHROPIC_API_KEY` 미설정 환경(로컬 기본 상태)에서 실제 업로드 실패를 발생시켜 DB에 `failed`+사용자 친화적 사유가 정확히 기록되는지, `#/ai-usage`에 배지·사유·재시도 버튼이 뜨는지, 재시도 클릭 시 새 행이 추가되고 한도가 다시 차감되는지(2/60→3/60) 헤드리스 브라우저로 확인 후 테스트 데이터 삭제
