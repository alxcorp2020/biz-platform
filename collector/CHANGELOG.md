- **🚨 채팅형 온보딩 타이핑 효과 — 여러 말풍선이 동시에 타이핑되던 문제 수정**: 직전 타이핑 효과 추가 직후 "여러 말풍선이 동시에 타이핑되는 것 같다"는 신고 — 원인은 `appendBotBubble`이 호출될 때마다 각자 독립된 `setInterval`을 즉시 시작해서, 예를 들어 인사말 두 번째 문장이 `chatDelay(500)`만 기다리고 뜨는데 첫 문장 타이핑엔 ~1000ms 이상 걸려 첫 문장이 아직 끝나기 전에 두 번째 문장도 동시에 타이핑을 시작해버렸던 것. 전역 프로미스 체인(`chatTypingQueue`)으로 모든 봇 말풍선의 타이핑을 직렬화 — 매 `appendBotBubble` 호출은 이 큐에 이어붙고, 직전 말풍선이 완전히 타이핑을 마치거나(또는 클릭으로 스킵되거나) 나서야 다음 말풍선이 DOM에 나타나고 타이핑을 시작한다. `appendBotBubble`의 반환값(rowEl)을 실제로 쓰는 호출부가 없어(grep 확인) 동기 반환을 포기하는 데 부담이 없었음. 로컬 헤드리스 브라우저로 페이지 로드 직후 100ms 간격으로 두 말풍선의 글자 수를 연속 샘플링 — 첫 번째 말풍선이 0→56자로 다 채워질 때까지 두 번째 말풍선은 DOM에 아예 나타나지 않고, 첫 번째가 완전히 끝난 시점(56자 고정)에야 두 번째가 0(또는 초기 몇 글자)부터 시작해 순차적으로 채워지는 것을 수치로 확인. `go build/vet/test`, `node --check` 통과.

- **🚨 신규 가입자 전원 빈 화면 무한루프 긴급 수정**: 사용자가 "신규 이메일가입/SNS로그인하면 사이드바 외 콘텐츠가 빈 화면, 메뉴 클릭해도 이동 안 됨"을 보고. 원인: `route()`의 온보딩 게이트 3개(약관동의/이메일인증/사업자등록증)가 각자 "자기 화면"만 예외로 뒀는데, 두 게이트의 조건이 동시에 참인 계정(예: 이메일가입 직후=onboarded true·emailVerified false·프로필 없음, 또는 소셜가입 직후=onboarded false·emailVerified true·프로필 없음)은 게이트A가 보낸 화면을 게이트B가 "내 예외 아님"이라며 다른 화면으로, 그 화면을 다시 게이트A가 원래 화면으로 — **두 게이트가 서로 무한 핑퐁**시켜 route()가 실제 화면 렌더링(dispatch)에 영영 도달하지 못했다(사이드바는 부팅 시 한 번만 그려져서 정상으로 보임 — 더 헷갈리게 만든 요인). 신규 가입자 전원(이메일/소셜 불문)이 100% 겪는 치명적 버그였다. 세 게이트를 각자의 좁은 예외 목록 대신 "온보딩 흐름에 속한 화면 전체"를 담은 공용 목록(`AUTH_ONBOARDING_ROUTES`) 하나로 통일해 근본 수정. 로컬에서 두 시나리오(이메일가입 직후 상태, 소셜가입 직후 상태) 모두 실제로 무한루프 재현 조건을 만들어 검증 — 수정 후 각각 정확히 한 번만 리다이렉트되어 올바른 화면에 정착하고, 전체 온보딩 완료 후 다른 메뉴로도 정상 이동되는 것까지 확인. 별개로 서비스워커의 `cache.put()`이 브라우저 확장 프로그램의 `chrome-extension://` 요청까지 가로채다 예외를 내던 버그도 함께 발견해 수정(http/https 스킴이 아니면 그냥 통과시키도록).
- **🚨 운영 마이그레이션 크래시 긴급 수정**: 사용자가 Render 로그에서 `schema migration failed: ... auth_lookup_attempts_kind_check ... violated by some row` 에러(반복 발생, 서비스 부팅 불가)를 보고. 원인: `ensureAuthLookupKindEmailVerifyResend`가 `ensureAuthLookupKindBizRegExtract`보다 먼저 실행되는데, 전자가 옛날(biz_reg_extract 추가 전) 좁은 CHECK 목록으로 매 부팅마다 DROP+ADD를 반복해 — 실제로 `biz_reg_extract` 행이 쌓인 뒤에는 그 좁은 ADD CONSTRAINT 자체가 기존 행과 충돌해 실패, 서버가 아예 못 뜸(무한 크래시루프). 이 정확한 버그 클래스는 `notification_log_event_type_check`에서 과거에 이미 한 번 발생·수정된 이력이 있었는데(`ensureDeadlineD7EventType` 주석 참고), 이번에 admin_broadcast/password_reset/email_verification 3개를 추가하면서 "새 함수 하나만 추가하고 이전 함수들은 그대로 두는" 실수를 반복해 그 4개 함수(`ensureDeadlineD7EventType`/`ensureReportEventTypes`/`ensureTeamInviteEventTypes`/`ensureAdminBroadcastEventType`)도 전부 옛날 좁은 목록에 멈춰 있었음을 함께 발견 — 운영에 password_reset/email_verification 알림 기록이 이미 쌓여있다면 다음 재기동 때 똑같이 크래시했을 잠재 사고. `auth_lookup_attempts.kind`/`notification_log.event_type` 두 CHECK 제약을 건드리는 함수 전부(총 8개)를 항상 "현재 최종" 전체 누적 목록으로 동기화해 근본 수정. 로컬에서 정확히 같은 방식으로 재현(운영과 동일한 에러 메시지 확인) 후, 수정한 코드로 같은 "오염된" DB 상태에서 연속 재기동 2회 모두 정상 기동되는 것까지 확인. **다음에 이 constraint들에 새 값을 추가할 때는 새 함수 하나만 추가하지 말고 `grep "notification_log_event_type_check"` 등으로 전부 찾아 함께 넓힐 것**(migrate.go의 `ensureDeadlineD7EventType` 주석에 재발 이력으로 남겨둠).
- **사업자등록증 등록을 하드 게이트로 승격**: Phase UX-01 최초 구현 때는 "나중에 하기"로 건너뛸 수 있는 소프트 유도였는데, 사용자가 "안 하면 절대 이동 불가"로 명시적으로 바꿔달라고 요청 — 휴대폰/이메일 인증과 같은 강제성으로 승격시켰다. `route()`에 새 게이트(`COMPANY_PROFILE_EXEMPT_ROUTES`) 추가 — `currentProfile`(loadMe()가 이미 채워둔 전역 상태, 새 필드 불필요)이 없는 `role==='user'` 계정은 `#/onboarding/business-registration`/`#/onboarding/complete`/`#/terms`/`#/privacy` 외 모든 경로에서 강제로 그 화면으로 돌려보낸다. `renderBusinessRegistrationOnboarding` 화면에 휴대폰/이메일 인증 화면과 같은 스타일(사이드바 숨김, `is-auth`)을 적용하고, 이제 기능하지 않을 "나중에 하기" 버튼은 제거 — 대신 AI 추출이 반복 실패하거나 사용자가 그냥 직접 입력하고 싶을 때를 위한 "직접 입력하기" 링크(빈 확인폼을 열어 완전 수동 입력 가능)를 남겨, 하드 게이트라도 업로드 자체를 강제하지는 않고 "회사 정보 등록"만 강제한다. 로컬 검증: 헤드리스 브라우저로 신규 가입 계정이 `#/`·`#/notices`·`#/pipeline`·`#/me/profile`·`#/calendar` 등 어디로 이동을 시도해도 전부 온보딩 화면으로 돌아오는 것 확인, "직접 입력하기"로 완전 수동 입력→회사 생성→게이트 해제→정상 네비게이션 재개까지 end-to-end 확인.

"판정불가" 사유는 지역/업종/기업규모 중 실제로 회사 프로필에 비어있는 필드를 동적으로 찾아 "OO 정보가 없어 N건을 정확하게 판정하지 못했습니다" 문구로 조합(판정엔진이 실제로 계산한 값이라 정확함). `GET /api/dashboard` 응답에 `eligibilitySummary` 필드 추가, 대시보드 완성도 카드 옆에 새 "추천공고 판정 현황" 카드로 표시. **의도적 범위 축소(사용자 확인 완료)**: 실적/인증/재무는 판정엔진에 기준 자체가 없어 "+N건" 같은 정확한 카운트를 낼 수 없음 — 이 세 항목은 완성도 점수 기반의 일반 안내 문구만 제공하고, 정확한 건수 계산이 필요한 새 판정기준 추가는 이번 범위에서 제외(사용자에게 명시적으로 확인받음). 기존 AI 분석엔진/DB 구조/추천엔진/관리자 기능/OCR 파이프라인 근간/공고 수집 로직은 전부 무변경. 로컬 검증: 마이그레이션 적용(신규 컬럼 4개+kind 확장) 확인, curl로 추출 엔드포인트(정상 요청 시 ANTHROPIC_API_KEY 미설정으로 인한 502 확인/미지원 파일형식 거부/내용불일치 거부/미인증 401/rate-limit 429), 확장된 `PUT /api/me/company-profile`(4개 신규 필드 저장+재조회 일치), `GET /api/dashboard`의 eligibilitySummary(4버킷 합계가 실제 열려있는 공고 수와 정확히 일치, 기업규모 입력 전/후 insufficientData→needsReview 이동 확인) 확인, 기존 면허 업로드 엔드포인트가 enum 변경 후에도 정상적으로 AI 한도 게이트까지 도달하는 것으로 회귀 확인, 헤드리스 브라우저로 온보딩 히어로→업로드 화면→확인 폼(AI 추출값 프리필)→확정→완료화면(실제 카운트 표시)→대시보드 판정현황 카드까지 전체 흐름 end-to-end 확인.
- **휴대폰 인증 사용여부 관리자 토글 + 이메일 가입 필수 이메일 인증 추가**: (1) `#/admin` 대시보드 "플랜 설정" 카드에 "회원가입 시 휴대폰 SMS 인증 사용" 체크박스 신설(`system_settings.phone_verification_required`, 기본값 `true` — 기존 동작 그대로 유지). 관리자가 끄면 `handleSignup`/`handleSignupAgreement`(이메일 가입/소셜로그인 온보딩 둘 다) 모두 휴대폰번호가 선택 입력이 되고 SMS 인증 없이도 가입 가능(값·형식 검증은 입력했을 때만 그대로 적용). 프론트는 공개 `GET /api/auth/config`로 이 값을 읽어 회원가입/소셜 온보딩 화면에서 OTP 발송·확인 UI(`otpPhoneFieldHtml`)를 보여줄지, 인증 절차 없는 선택 입력 하나(`plainPhoneFieldHtml`)만 보여줄지 결정한다. (2) 이메일 가입은 이제 필수 이메일 인증을 거친다 — 계정은 가입 즉시 생성/로그인되지만(`email_verification.go`), 인증 링크(`#/auth/verify-email?token=...`, 24시간 유효, SHA-256 해시 저장, 1회용)를 클릭하기 전까지는 `route()`가 대부분의 화면 접근을 막고 재발송 버튼이 있는 대기 화면(`#/auth/verify-email-pending`)으로 돌려보낸다. 소셜 로그인(구글/네이버/카카오)은 제공자가 이미 검증한 이메일이라 계정 생성 시점(`oauth_login.go`)에 바로 인증 완료 처리되어 이 게이트를 거치지 않는다. **"온보딩 완료" 판정 기준 재조정**: 휴대폰 인증이 선택이 될 수 있게 되면서 `phone_verified_at`만으로는 더 이상 온보딩 완료 여부를 판단할 수 없어져, `handleMe`가 `terms_agreements` 행 존재 여부로 계산한 `onboarded` 필드를 새로 내려주고 `route()`의 소셜로그인 온보딩 가드가 이 값을 쓰도록 전환(`phoneVerified` 자체는 정보용으로 유지). 재발송(`POST /api/me/resend-verification-email`)은 이미 인증된 계정이면 거부하고, [[아이디 찾기/비밀번호 찾기]] 기능에서 만든 `auth_lookup_attempts` 공용 남용방지 테이블에 `email_verify_resend` kind를 추가해 재사용(같은 계정 1분 1회, 1일 5회). 기존 회원 전원은 마이그레이션이 일괄 백필(`email_verified_at = created_at`)해 새 게이트의 영향을 받지 않음 — 이 백필은 컬럼이 "처음" 추가될 때 딱 한 번만 실행되도록 information_schema로 방어(안 그러면 매 서버 재시작마다 새로 가입한 미인증 사용자까지 자동으로 인증완료 처리되는 버그가 생김). 로컬 검증: 관리자 토글 on/off 전환 후 각각 회원가입(휴대폰 필수/선택) 성공 확인, 토글 off 상태에서 형식 오류 전화번호는 여전히 거부되는 것 확인, 이메일 인증 전체 흐름(가입→대기화면 강제이동→다른 화면 접근 차단→재발송 rate-limit→링크 클릭→인증완료→접근 허용) curl+헤드리스 브라우저로 end-to-end 확인, 기존 회원 9명 전원 `email_verified_at` 백필 확인, 관리자 체크박스 UI 클릭→저장까지 확인. **구현 중 발견해 함께 고친 연쇄 버그 2건**(휴대폰 인증을 선택으로 바꾸면서 파생됨): (1) `handleUpsertCompanyProfile`이 최초 회사 프로필 생성 시 `phone_verified_at IS NOT NULL`을 무조건 요구해, 토글을 끈 뒤 가입한(휴대폰 인증을 아예 안 거친) 회원은 회사 프로필을 영원히 못 만드는 상태가 될 뻔함 — 이 가드를 phoneRequired 설정값 조건부로 바꿔 고침. (2) `oauth_login.go`의 콜백 리다이렉트가 `phone_verified_at` 기준으로 온보딩 화면 이동을 판단해, 이미 약관동의까지 마쳤지만 휴대폰 인증은 한 적 없는(토글 off 상태에서 가입한) 소셜 로그인 회원이 로그인할 때마다 매번 온보딩 화면으로 튕기게 될 뻔함 — `terms_agreements` 존재 여부 기준으로 바꿔 고침(handleMe의 onboarded와 동일 기준). 두 버그 모두 로컬 curl 재검증(토글 off로 가입한 계정의 회사 프로필 생성 성공, 토글 on 계정은 기존과 동일하게 정상 동작) 완료.
- **아이디(이메일) 찾기 + 비밀번호 찾기 추가**: 로그인 화면에 "아이디/비밀번호 찾기" 링크(`#/auth/find-account`, 탭 2개)를 신설. **이메일 찾기**(`POST /api/auth/find-email`, `find_email.go`)는 가입 시 인증된 휴대폰번호로 계정을 조회해 이메일을 `ab***@domain.com` 형태로 마스킹해 보여준다(로컬파트 앞 2글자만 남기고 나머지는 원래 길이와 무관하게 항상 `*` 3개). 본인인증은 우선 "가입 시 등록한 휴대폰번호 입력"만으로 최소 구현(SMS 인증코드 재확인은 SMS 인프라 비용 문제로 이번엔 생략, 추후 추가 예정). **비밀번호 찾기**(`POST /api/auth/reset-password-request` + `POST /api/auth/reset-password`, `password_reset.go`)는 이메일 입력 → 계정이 존재하고 비밀번호가 있는(소셜로그인 전용 아닌) 경우에만 기존 Resend 인프라로 재설정 링크(`#/auth/reset-password?token=...`, 1시간 유효, SHA-256 해시로 저장, 1회용) 발송 → 링크 클릭 시 새 비밀번호 설정 화면. **anti-enumeration**: reset-password-request는 계정 존재/소셜전용 여부와 무관하게 항상 동일한 200 응답을 반환(표준 관행) — find-email은 반대로 "인증 후 표시"가 기능 스펙 자체라 계정 존재 여부가 결과에 그대로 드러난다. 두 조회 모두 OTP 챌린지가 없어 신규 `auth_lookup_attempts` 테이블로 phone_verifications와 같은 기준(같은 identifier 1분 1회, 1일 5회)의 남용 방지를 공용 적용(`authLookupRateLimited`). 신규 `password_reset_tokens` 테이블 추가, `notification_log.event_type` CHECK에 `password_reset` 추가. 세션이 HMAC 서명 쿠키라 서버측 세션 테이블이 없어 비밀번호 재설정이 다른 기기의 기존 세션을 무효화하지 않는 것은 기존 아키텍처 한계로 이번 범위에서 다루지 않음. 로컬 검증: curl로 이메일 찾기(정상/미가입/형식오류/rate-limit 429) 및 비밀번호 찾기 전 구간(정상 발송 로그·소셜전용 계정 제외·존재하지 않는 이메일과 응답 동일·토큰 무효/만료/재사용/짧은 비밀번호 거부·정상 재설정 후 새 비밀번호로 로그인 성공, 구 비밀번호 거부) 확인, 헤드리스 브라우저로 로그인 화면 링크→탭 전환→이메일 찾기 결과 표시→비밀번호 재설정 요청 안내 문구→토큰 포함 링크 접속→새 비밀번호 제출→완료 화면까지 end-to-end 확인.

- **회원가입 휴대폰번호 입력 자동 하이픈 포맷**: 회원가입 1단계(계정정보)와 2단계(소셜 로그인 가입자용 휴대폰번호 입력란)에서 숫자만 입력해도 자동으로 하이픈이 붙도록 개선(`formatMobilePhoneInput`+`attachPhoneAutoFormat`, index.html). 010은 11자리(3-4-4: 010-1234-5678), 011/016/017/018/019(구 통신사 번호)는 10자리(3-3-4: 011-123-4567)로 자릿수 자체가 달라 첫 3자리(prefix)로 어느 쪽인지 판단해 포맷. `pattern` 속성과 서버측 검증 정규식(`signup_agreement.go`의 `phoneNumberPattern`)도 두 형식 모두 허용하도록 함께 갱신(기존엔 010 11자리만 허용해 그 외 번호는 가입 자체가 막혀 있었음). 사업자 대표전화번호(회사 대표번호, 랜드라인 등 형식이 다양함)는 이 자동포맷 대상에서 제외 — 개인 휴대폰번호 입력란에만 적용. 로컬 검증: node로 진행형 타이핑 시뮬레이션(010/011 각각 자릿수별 중간 상태) 확인, 헤드리스 브라우저로 실제 입력 필드에 키 입력 시뮬레이션 후 자동 포맷 스크린샷 확인, 011-123-2345로 회원가입 전체 흐름 완료해 DB에 정확히 저장되는 것까지 확인.
- **관리자 회원관리에 "회원 삭제"(완전 삭제) 추가**: 기존 "탈퇴 처리"(익명화, 데이터 보존)와 달리 개발 단계에서 반복 생성하는 테스트 계정을 흔적 없이 지우기 위한 하드 삭제(`DELETE /api/admin/members/{id}`, `handleAdminDeleteMember`). 대상이 회사(company_profiles)의 owner면 그 회사에 딸린 모든 데이터(문서/면허·인증/재무·실적·인력/파이프라인+체크리스트/담당자/구독/결제기록/리포트/알림이력 등, `company_documents`를 가리키는 `company_profiles.employee_count_source_document_id` 순환참조는 먼저 NULL로 끊음)까지 트랜잭션으로 함께 삭제. 안전장치 2가지: (1) 다른 팀원이 남아있는 조직의 owner는 삭제 거부(`owner_has_other_members`, 탈퇴 처리와 동일 정책 — 하드 삭제라 다른 팀원의 접근 권한이 예고 없이 사라지는 게 더 위험해서), (2) 관리자 자기 자신은 삭제 불가(`cannot_delete_self`, 복구 수단이 없어서). 프론트는 "탈퇴 처리" 버튼 옆에 "회원 삭제" 버튼을 추가하고, `confirm()` 하나로는 부족하다고 판단해 이메일 주소를 그대로 입력해야 진행되는 "타이핑 확인" 방식(`prompt()`)을 추가 안전장치로 둠. 로컬 검증: 자기 자신 삭제 시도 400 차단, 팀원 있는 owner 삭제 시도 409 차단(팀원 먼저 삭제 후 재시도하면 성공), 정상 삭제 후 company_profiles/company_members가 정확히 0건인 것을 DB에서 직접 확인, 헤드리스 브라우저로 실제 버튼 클릭→prompt 입력→삭제 완료→회원목록으로 리다이렉트까지 end-to-end 확인.
- **회원가입 2단계 마법사 재구성(계정정보 → 업체정보) + 소셜가입 필수정보 우회 차단**: 기존엔 1단계(이메일/비밀번호)에서 바로 계정을 만들고 2단계(회사정보)에서 개인 휴대폰번호+약관동의를 받았는데, 이를 1단계=계정정보(휴대폰번호+이메일+비밀번호+비밀번호확인), 2단계="업체정보"(사업자 지역/업종/기업규모/사업자 대표전화번호+약관동의)로 재구성. **계정 생성 시점을 2단계 "가입하기"로 미룸**(1단계 "다음 단계"는 이제 클라이언트 검증만 하고 서버에 아무것도 안 남김) — 그 결과 2단계에서 "이전으로"로 1단계를 왕복해도 이메일 중복가입 걱정 없이 자유롭게 값이 유지된다(모듈 레벨 `signupStep1Data`/`signupStep2Data`로 왕복 보존, 팀 초대 경유 가입은 예전처럼 1단계에서 즉시 계정생성+2단계 스킵 유지). 사업자 지역은 자유 텍스트에서 기존 17개 광역시도+전국 select(`REGION_OPTIONS`)로, 기업 규모도 자유 텍스트에서 새 `COMPANY_SIZE_OPTIONS`(소상공인/소기업/중기업/중견기업/대기업, eligibility.go의 `소기업` 판정과 정확히 일치) select로 전환. 사업자 대표전화번호(회사 단위, 개인 휴대폰번호와 별개)는 새 필드로 `company_profiles.phone_number`에 저장(과거 "조직 알림용, 미사용" 코멘트가 붙어있던 컬럼을 이 용도로 재활용, 회사정보 수정 화면에도 같은 필드 추가). **소셜 로그인(구글/네이버/카카오) 가입자는 1단계를 거치지 않으므로**(OAuth 콜백이 계정을 이미 만들고 바로 2단계로 보냄) 개인 휴대폰번호를 물어볼 기회가 영영 없어지는 문제가 생겨, 2단계 화면이 `fromEmailStep1` 여부로 개인 휴대폰번호 입력란을 조건부 표시(이메일 가입자는 1단계 값을 그대로 제출에 실어 보내 다시 안 물어봄, 소셜 가입자는 반드시 입력). **서버측 방어 추가**: `handleUpsertCompanyProfile`(최초 생성 시점)이 `users.phone_number`(개인)와 요청의 사업자 대표전화 둘 다 없으면 각각 `phone_number_required`/`business_phone_required`로 거부 — UI가 항상 signup-agreement(전화번호+약관) → company-profile 순서로 호출하는 것과 무관하게, 어떤 경로(직접 API 호출 등)로도 "전화번호 입력 없이 회사 프로필(=가입완료 판정 기준인 company_members)이 생성"되는 걸 서버 레벨에서 막는다 — oauth_login.go의 `hasProfile` 판정이 company_members 존재 여부만 보므로 이 가드가 없으면 그 판정을 우회할 수 있었음. 로컬 검증: curl로 signup-agreement를 건너뛰고 바로 company-profile을 호출하면 이메일/소셜 가입 시나리오 둘 다 400으로 막히는 것 확인, 헤드리스 브라우저로 1→2→이전으로→2 왕복 시 두 단계 값 모두 유지되는 것, 이메일 가입 전체 흐름과 소셜가입 시뮬레이션(1단계 없이 2단계 진입 시 휴대폰번호 입력란이 뜨는 것) 각각 끝까지 완료해 DB에 개인 휴대폰번호+사업자 대표전화가 정확히 분리 저장되는 것 확인.
- **로그인/가입 화면 깜빡임(FOUC) 제거 + 카드 중앙정렬 수정**: 직전 라우트 접근제어 작업에서 나온 UI 버그 2건. (1) 페이지 로드/이동마다 사이드바 있는 레이아웃이 잠깐 보였다 사라지는 현상 — 원인 두 가지를 각각 수정. 정적 `<body>`에 처음부터 `app-booting` 클래스를 박아 앱 셸(사이드바/헤더/탭바/전역배너)을 `visibility:hidden`으로 가리고 그 위에 로딩 스피너 오버레이만 보이게 했다가, `await loadMe(); route();`가 완전히 끝난 뒤에야 같은 동기 틱에서 클래스를 제거(초기 로드 FOUC). `route()`가 `#/` 경로일 때 `renderHome`의 비동기 대시보드 API 응답(401 감지)을 기다리지 않고, 이미 확정된 `currentUser` 값으로 `is-landing` 여부를 그 자리에서 동기적으로 결정하도록 변경(네비게이션 시 깜빡임). (2) 로그인/가입 카드가 화면 오른쪽으로 치우쳐 보이던 버그 — `body.is-auth main#app`이 `display:flex`인데 `flex-direction`을 지정 안 해 기본값 `row`로 동작, 형제 요소였던 로고(`<a class="auth-page-logo">`)와 카드(`.auth-card`)가 나란히 배치되면서 전체 그룹이 중앙에 있어도 로고가 왼쪽·카드가 오른쪽으로 나뉘어 보였던 것. 로고를 카드 형제가 아니라 카드 안쪽 최상단으로 옮기고, `main#app`에 `flex-direction: column` 추가, `.auth-card`의 `border-radius`를 하드코딩 값(14px)에서 공용 토큰 `--radius-card`(20px)로, padding을 2rem→2.5rem로 확대, 배경을 `--bg`→`--bg`에서 `--bg-soft`로 내려가는 은은한 그라데이션으로 변경. 로컬 검증: 네트워크를 인위적으로 늦춘(`Network.emulateNetworkConditions`) 상태에서 로딩 중간 시점을 캡처해 셸이 전혀 안 보이고 스피너만 뜨는 것을 로그인 상태/비로그인 상태(랜딩) 양쪽 다 스크린샷으로 확인, 로그인/가입 카드가 화면 정중앙(수직+수평)에 로고-제목-폼 순서로 표시되는 것 확인.
- **라우트 접근제어 정리**: 비로그인 상태에서 `#/notices`(공고검색) 등 내부 화면이 그대로 노출되던 문제 수정. 조사 결과 `#/notices`는 서버(`handleListNotices`)가 원래 비로그인도 200을 주는 옵셔널 인증 설계인 데다, 프론트가 상태코드를 보존 안 하는 `fetchJSON`을 써서 401 감지 자체가 불가능한 구조라 실제로 데이터가 새고 있었음(`#/pipeline`/`#/calendar`/`#/growth` 등 나머지는 서버가 401을 강제하고 프론트도 리다이렉트 코드가 있어 결과적으로는 안전했으나, 각 render 함수가 API 응답을 받은 뒤에야 뒤늦게 리다이렉트하는 분산된 방식이었음). `route()` 함수 진입 시점에 화이트리스트(`PUBLIC_ROUTES`) 기반 가드를 추가해 렌더 시작 전에 즉시 차단하는 방식으로 통일 — 공개: `/`, `#/announcements`(+상세), `#/terms`, `#/privacy`, `#/auth/login`, `#/auth/signup`, `#/invite`, `#/billing/plans`(요금비교는 가입 전에도 봐야 함), `#/billing/fail`. 나머지 전부(`#/notices`, `#/pipeline`, `#/calendar`, `#/notifications`, `#/me/*`, `#/growth`, `#/admin/*` 등)는 비로그인 시 `#/auth/login`으로 즉시 리다이렉트. **선행 버그 수정**: `loadMe()`(비동기)가 `await` 없이 호출되고 바로 `route()`가 실행되던 부팅 순서 때문에, 가드를 그대로 추가하면 실제 로그인 사용자도 새로고침마다 한 박자 로그인화면으로 잘못 튕기는 레이스컨디션이 있어 `await loadMe(); route();` 순서로 고침.
- **로그인/회원가입 화면 심플화**: `body.is-auth`(랜딩페이지의 `is-landing`과 동일 원리) 적용 시 사이드바·헤더·탭바·프로필배너를 숨기고 `#app`을 화면 중앙(세로까지) 정렬, 카드 위에 브랜드 로고 추가. 회원가입 2단계(연락처+약관동의, 같은 `#/auth/signup` 해시를 유지한 채 컨테이너만 갈아끼우는 구조)는 의도적으로 일반 사이드바 레이아웃으로 되돌림 — 소셜 로그인 경유 2단계(`#/auth/oauth-profile`)와 레이아웃을 통일하기 위함.
